# ProdFlow

**ProdFlow** — учебный backend-проект: REST API для управления производственными заказами на изготовление партий деталей. Система позволяет вести каталог деталей и технологических операций, управлять станками, принимать заявки заказчиков и моделировать последовательное выполнение производственных этапов.

Проект реализован как монолитное приложение на Java и Spring Boot. Пользовательского веб-интерфейса нет: взаимодействие происходит через HTTP API.

## Возможности

- **Пользователи и роли:** регистрация заказчиков, подтверждение и отклонение регистрации, управление учётными записями; роли `CUSTOMER`, `ADMIN`, `SUPER_ADMIN`.
- **Каталог деталей:** создание и редактирование деталей, архивация, восстановление, проверка доступности для производства.
- **Технологические маршруты:** упорядоченная последовательность операций, необходимых для изготовления детали.
- **Оборудование:** привязка станков к операциям, учёт занятости, обслуживание и архивация.
- **Заявки на новые детали:** заказчик предлагает деталь, администратор одобряет заявку и определяет технологический маршрут либо отклоняет её.
- **Заказы:** оформление партии выбранной детали, изменение и отмена новых заказов, просмотр истории.
- **Планирование производства:** автоматическое назначение доступных станков, выполнение операций в заданном порядке, отслеживание статусов заказа и оборудования.

## Как работает производство

1. Администратор заводит технологические операции и станки, способные их выполнять.
2. Для детали задаётся **маршрут** — последовательность операций.
3. Заказчик оформляет заказ на изготовление партии. Для заказа создаются производственные этапы с зафиксированными порядком и длительностью операций.
4. Планировщик выбирает готовые этапы в порядке поступления и назначает на них подходящие свободные станки.
5. Партия проходит операции **последовательно**: следующий этап становится доступен после завершения предыдущего.
6. После завершения всех этапов заказ получает статус `COMPLETED`.

Если операцию одновременно выполняют несколько станков, продолжительность этапа определяется количеством необходимых циклов обработки:

```text
cycles = ceil(quantity / machineCount)
duration = cycles * timePerPart
```

Планировщик запускается каждые 5 секунд. Расчётное время завершения этапа хранится в PostgreSQL, поэтому после перезапуска приложения просроченные этапы могут быть обработаны при следующем запуске планировщика.

## Запуск локально

### Требования

- JDK 21;
- Maven;
- Docker с поддержкой Docker Compose.

### 1. Настроить PostgreSQL

Создайте в корне проекта файл `.env`:

```dotenv
DB_USERNAME=prodflow_user
DB_PASSWORD=replace_with_your_password
```

Запустите контейнер с базой данных:

```bash
docker compose up -d
```

PostgreSQL будет доступна на `localhost:5432`, имя базы — `prodflow`. При первом запуске приложения схема создаётся из `src/main/resources/schema.sql`; Hibernate проверяет соответствие сущностей схеме (`ddl-auto: validate`).

### 2. Запустить приложение

Задайте приложению переменные окружения `DB_USERNAME` и `DB_PASSWORD` с теми же значениями, что и в `.env`. **Docker Compose читает `.env`, но сам по себе не передаёт эти переменные процессу Java**, запущенному отдельно.

Запустите `ProdFlowApplication` из IDE или выполните команду в терминале, где уже заданы переменные окружения:

```bash
mvn spring-boot:run
```

REST API по умолчанию доступен по адресу `http://localhost:8080`.

### 3. Создать первого супер-администратора

Регистрация через API создаёт только пользователей `CUSTOMER` со статусом `PENDING`. Для первоначальной настройки необходимо вручную добавить учётную запись `SUPER_ADMIN` в PostgreSQL:

```sql
INSERT INTO users (name, email, password_hash, role, status)
VALUES (
    'zero_admin',
    'admin@prodflow.local',
    '<BCrypt-хеш выбранного пароля>',
    'SUPER_ADMIN',
    'APPROVED'
);
```

В `password_hash` должен находиться **настоящий BCrypt-хеш**, а не пароль в открытом виде. Его можно получить с помощью `BCryptPasswordEncoder` из Spring Security. Логин для HTTP Basic — адрес электронной почты пользователя.

## Авторизация и роли

Приложение использует HTTP Basic и не хранит HTTP-сессии. Только `POST /api/users/register` доступен без авторизации; остальные маршруты требуют входа.

| Роль | Доступ |
|---|---|
| `CUSTOMER` | Собственные заказы и заявки, управление своим профилем |
| `ADMIN` | Управление каталогом, оборудованием, заявками и заказами, модерация заказчиков |
| `SUPER_ADMIN` | Полномочия администратора и управление администраторами |

Новые пользователи не могут авторизоваться до подтверждения регистрации (`APPROVED`).

## Основные разделы API

| Адрес | Назначение |
|---|---|
| `/api/users` | Регистрация, профили, роли и статусы пользователей |
| `/api/operations` | Технологические операции |
| `/api/machines` | Станки и обслуживание оборудования |
| `/api/parts` | Каталог деталей |
| `/api/part-requests` | Заявки на новые детали |
| `/api/orders` | Производственные заказы |

API использует JSON и стандартные HTTP-коды ответа, в том числе `400`, `401`, `403`, `404` и `409` для соответствующих ошибок.

## Тестирование

В проекте предусмотрены интеграционные тесты сервисов и коллекция Postman для проверки REST API, правил доступа и сквозного производственного сценария.

Для запуска тестов Java:

```bash
mvn test
```

**Примечание:** интеграционные тесты используют PostgreSQL из конфигурации приложения, а не встроенную тестовую БД. Перед запуском убедитесь, что база доступна и подготовлена; для тестов желательно использовать отдельную локальную базу.

### Коллекция Postman

Импортируйте JSON-файлы коллекции и окружения в Postman. Выберите окружение `ProdFlow Local`, укажите пароль тестового супер-администратора в переменной `superAdminPassword` и запускайте **папки по отдельности** через Collection Runner:

| Папка | Режим приложения | Что проверяется |
|---|---|---|
| `01 · REST API | scheduler OFF` | `PRODFLOW_SCHEDULER_ENABLED=false` | CRUD, валидация, бизнес-правила, права доступа |
| `02 · Production Flow | scheduler ON` | `PRODFLOW_SCHEDULER_ENABLED=true` | Создание заказа и автоматическое завершение производства |

Значение `PRODFLOW_SCHEDULER_ENABLED` устанавливается через переменные окружения при запуске Java-приложения. Между режимами приложение необходимо перезапустить. Тест производства выполняется дольше: этапы моделируются в реальном времени.

**Внимание:** Postman-тесты создают и изменяют записи в выбранной базе данных. Автоматической очистки данных после выполнения коллекции нет.

## Ограничения текущей версии

- Один заказ — партия одного типа детали.
- Этапы производства выполняются последовательно, без конвейерной передачи отдельных деталей.
- Станок поддерживает один тип операции; одну операцию могут выполнять несколько станков.
- Время производства рассчитывается по длительности операции, количеству деталей и числу назначенных станков.
- Взаимодействие с системой предусмотрено через REST API; графического интерфейса нет.
